# 04 AI 智能问答

首页右下角的悬浮问答。后端走检索增强：把当前版本的简历内容切成知识块、向量化，按问题取最相关的若干块塞进 prompt 交给大模型；任何一环不可用都降级到本地问答，保证访客问什么都拿得到实质回答。

## 知识库的构建

`buildKnowledgeBase(versionId)` 把六类内容拼成一份带栏目标记的纯文本（`AiService.java:149-251`）：基本信息逐字段输出（姓名、职位、标语、邮箱、电话、微信、三个代码托管地址、所在地、个人简介，`:155-167`），教育/经历/技能按 sort 与日期排序逐条输出成 `- ` 开头的行（`:170-207`），荣誉与作品集先用该版本的 profile.name 当归属人查（`:210-249`），查不到姓名就整段跳过。

也就是说：荣誉和作品能不能进 AI 上下文，取决于这个版本的 profile 里姓名填了没有，跟版本本身有没有内容无关。改名之后问答"忘记"了原来的荣誉证书，原因就在这里。

分块按行规则做（`chunkKnowledgeBase`，`AiService.java:353-393`）：

- `【基本信息】` 段落整体作为一个块，并且总是放在列表首位（`:389-391`）。
- 其余栏目每条记录成一个块，块文本带上栏目标题（`:374-375`）。
- 以 `职责/描述：`、`技术栈：` 开头或原本缩进两格的行，并入上一个块而不是单独成块（`:376-382`）。

## 检索

```java
// AiService.java:290-309 摘要
LinkedHashSet<Integer> selected = new LinkedHashSet<>();
// 基本信息块强制入选，保证姓名/求职意向/联系方式这类事实始终在上下文里
if (chunks.get(0).startsWith("【基本信息】")) selected.add(0);
// 其余按余弦相似度降序取，低于 0.15 的不选（selected 为空时例外，至少给一个）
if (sc.score() >= 0.15 || selected.isEmpty()) selected.add(sc.index());
```

三个数字记在这里：阈值 **0.15**（`:306`）、条数 **top-k 默认 6**（`application.yml:103`）、基本信息块**无条件占用一个名额**（`:292-294`）。阈值这么低是因为中文嵌入模型在不同厂商之间分值分布差别很大，0.4 以上的过滤在实际语料里会把大部分块都滤掉，宁松勿紧，反正 prompt 里已经写了"没有相关内容就如实说明"。

相似度是普通余弦：点积除以两个模长之积，维度不等或任一模长为 0 直接返回 0（`cosineSimilarity`，`AiService.java:449-465`）。向量类型是 `float[]` 不是 `double[]`，嵌入接口返回的数组逐个 `asDouble()` 再窄化（`:432-436`）。

选中的块按 `LinkedHashSet` 的插入顺序拼接（`:311-315`），即基本信息在最前、其余按分数降序；结果为空字符串时再退回全量知识库（`:317`）。

## 向量缓存

没有用 Spring 事件，也没有版本变更通知。缓存失效靠**内容签名比对**：

```java
// AiService.java:78 缓存条目形状
private record KbCache(String signature, List<String> chunks, List<float[]> vectors) {}

// AiService.java:328-346 摘要
String signature = kbSignature(knowledgeBase);      // :329
if (cached != null && cached.signature().equals(signature)) return cached;  // :331-333
synchronized (vectorCache) {                        // :334  双重检查后重建
    ...
    vectorCache.put(versionId, fresh);              // :342
}
```

签名是整个知识库文本的 SHA-256 取前 16 个十六进制字符（`kbSignature`，`:468-480`），摘要算法异常时退化成 `content.hashCode()`。内容一改签名就变，下一次问答自动重建，不需要任何模块通知——版本服务和 AI 服务之间没有任何耦合，这比事件方案少一套类，代价是"改没改"要等下一次请求才知道。

缓存键是 versionId，`Map<Long, KbCache>` 用 `ConcurrentHashMap`（`:75-76`），重建段用 `synchronized (vectorCache)` 包住，防止并发首次问答把同一版本嵌入两遍。缓存不主动淘汰，版本删了条目还在，量级是每版本几十个向量，可以不管。

## 调大模型

`callLlm`（`AiService.java:485-542`）用 JDK 自带 `java.net.http.HttpClient`，connectTimeout 10 秒（`:46-48`），请求超时用 `app.ai.timeout`（`:524`）。请求体 `model` / `messages` / `temperature=0.7`（`:517-521`），响应取 `choices[0].message.content`（`:537`），空内容也抛异常走降级。

system prompt 里除了"只能依据知识库回答、没有就如实说明"，还专门写了一段**时间判断规则**（`:493-500`）：把当前日期注入 prompt，规定"毕业日期早于或等于当前日期就必须回答已毕业"、"简历里写'预计毕业'但日期已过按已毕业回答"。加这段的原因是简历文本里的时间是绝对的（`2020-09-01 ~ 2024-06-30`），模型很爱顺着原文的"预计"字样输出过期结论，访客问"什么时候毕业"就会答错。这类只有真被访客问过才会写进 prompt 的规则，是这份代码里比较值得留意的部分。

多轮上下文从库里回捞，不靠前端传历史：按会话键取最近 `HISTORY_LIMIT = 6` 条（`:35,505-509`），倒序查出来再 `Collections.reverse` 复原成正序（`:510`），逐条转成 user/assistant 消息对，最后追加本次问题（`:511-515`）。前端只要把接口返回的 sessionId 存住回传即可，`views/home/AiChatWidget.vue:124-132` 用的 key 是 `resume-ai-sid`，生成规则是 `Date.now()` 加一段 36 进制随机数——注意与访问上报用的 `resume-sid`（`ResumeHome.vue:254-261`）是两个不同的键，不要合并。

会话键不是裸的 sessionId，而是 `sessionId + "#" + versionId`（拼键 `:112-115`，写入 `:133`，回捞 `:507`）。要断开的是上下文而不是知识库：知识库每次问答都按版本重拼，向量缓存又以版本号为键，本来就不会跨版本；但 `ai_chat_history` 没有版本列，`resume-ai-sid` 存在 localStorage 里换版本也不重置，同一浏览器先在 A 版本问几轮再进 B 版本时，A 版本的最近 6 轮问答会连同 B 版本的知识库一起进 prompt，模型会把 A 版本的内容复述进 B 版本的回答。触发场景有两个：管理员从后台带 `?versionId=` 预览另一个版本，以及「跟随默认」的专属链接在站长切换默认版本之后被同一个访客继续用。绑定了具体版本的链接不受影响。

键拼在服务端而不是让前端换 key，理由是默认版本由服务端解析（第 03 篇的 `resolveVersionId`），前端在「跟随默认」这条路上根本不知道当前版本号；拼在服务端一处，管理员与访客两种身份都覆盖。也没有选「给 `ai_chat_history` 加 `version_id` 列再按列过滤」：建表走 `CREATE TABLE IF NOT EXISTS`，新列对已存在的库不生效，得再补一条 ALTER 迁移，而键里带后缀一行代码就断开，历史表结构不动。截断顺序有讲究——`session_id` 列宽 64（`schema.sql:8`），必须先把 sessionId 截短再拼后缀，反过来一旦超长就会把后缀截掉，两个版本重新并流（`:111-115`）。

后缀只在库里存在，对外一律看不出来：接口返回的仍是前端传来的原 sessionId（`:140`），system prompt 里没有版本号（`:493-500`），访客侧没有任何文案出现「版本」字样。后台问答记录页要按会话筛，就复制列表里的完整值。走本地降级的回答不受影响，`localAnswer` 全程不读历史（`:548-669`）。

这条改动上线时有一个一次性副作用：历史表里的旧记录是不带后缀的裸 sessionId，和新的回捞键匹配不上，于是所有在途会话的多轮上下文清零一次（旧记录本身还在，后台照常可查）。不改数据、不补迁移，代价只有这一轮。

每轮问答都落库，字段 `sessionId / question / answer / source`，source 取 `llm` 或 `local`（`:132-137`）。落库的 `sessionId` 是带版本后缀的会话键，因此后台记录页那一列同时能看出这条回答出自哪个版本。问答记录页据此能区分哪些回答是大模型给的、哪些是本地兜底的，`source` 的分布也是判断嵌入额度够不够的依据。

## 本地降级

进入条件两个：`api-key` 为空（`:116,127-130`），或调用过程中抛任何异常（`:122-125`）。

`localAnswer`（`:548-669`）不是"关键词命中几个就选几个块"，而是**意图分支 + 栏目抽取**：按问题文本匹配十几个意图（问候、出生年龄、联系方式、荣誉、工作、项目、技能、教育、求职意向、个人评价、身份介绍），命中就直接 `extractSection(knowledgeBase, "【对应栏目】")` 返回整段（`:829-839`），没有对应栏目内容则回一句"暂未维护××信息"。关键词表写死在代码里（`:590-628`），一份是口语说法（"拿过什么奖""上学"），一份是该简历方向里的工具与术语（`postman`、`adb`、`iperf`、`uni-app`、`性能测试` 这类），换岗位方向时这一批词要重挑，不改也能跑，只是命中率下降。

没命中任何意图时做全文检索兜底（`searchKnowledge`，`:722-799`）：把问题拆成英文词（`WORD_PATTERN`，`:826-827`）加中文 2 字/3 字滑窗 gram，先剔除口语词表 `STOP_WORDS`（`:815-824`，"的了吗呢"这类单字全在里面），再对知识库逐行计分（长度 ≥3 的 token 命中记 2 分，短 token 记 1 分），按分数降序后每个栏目最多取 2 行、总共最多 6 行（`:773-786`），最后按知识库原栏目顺序聚合输出，开头一句固定为 `:793` 的 `根据简历内容，为你找到以下相关信息：`（原文串，非笔记表述）。

全部落空时返回简历速览 `overviewAnswer`（`:685-716`）：基本信息 + 教育 + 技能 + 工作 + 项目 + 荣誉拼成一段，末尾给几条可换的问法。兜底文案见 `:687`，形如 `这个问题我没在简历里找到完全对应的信息，先为你奉上 …… 的简历速览`（原文串，非笔记表述），而不是一句「抱歉，不清楚」——访客拿到空回答就不会再问第二次，这个分支的存在就是为了保住续问率。

## 前端组件

`components/home/AiChatWidget.vue`：右下角悬浮球，点开是宽 390px、高 580px 的面板（`max-height 72vh`，`:246-250`），三段结构 header / 消息区 / 输入区。首次访问自动弹开，用户手动关过一次就不再自动弹，标记是 `localStorage['resume-ai-auto-opened']`（`:103-110`）。四条快捷问题覆盖技能、实习、荣誉、毕业时间与联系方式（`:117-122`），每条都落在 `localAnswer` 的意图分支上，保证未配置大模型时点任意一条都有实质回答。

发送流程 `send()`（`:161-180`）：trim 后非空且非 loading → 立刻 push 用户消息 → 调 `aiChat({sessionId, question, versionId})` → push 回答并带上 `source`。失败时 push 固定文案「抱歉，问答服务暂时不可用，请稍后再试。」并把 source 标为 `error`（`:181-186`）。

回答按行结构化渲染，`【…】` 当标题、`-`/`•`/`·`/`*` 开头当列表项、其余当段落（`:134-148`），没有引入 markdown 库。等待态是三个圆点的 blink 动画（`:54-61,476-496`），不是逐字打字效果——逐字输出要靠流式接口，这里一次请求拿全量回答，做假打字只会拖慢首字时间。

两个细节：回车发送时屏蔽输入法合成态，`e.isComposing || e.keyCode === 229` 时不触发（`:150-154`），否则拼音选词回车会把半截问题发出去；面板在小屏上不隐藏，只有一个 `@media (max-width: 480px)` 把 right 调成 -8px（`:261-266`），全局也没有隐藏该组件的规则。

## 可复用点

- **每个外部依赖都写明降级触发条件**：对话缺 key 或抛任何异常都落到本地问答（`AiService.java:116,122-130`），嵌入地址留空则跳过向量检索、直接用全量知识库（`:280-282`）。抄到别的项目时最容易漏的是"降级要有名字"——`source` 字段把 `llm` 与 `local` 记进库（`:132-137`），后台才看得出降级发生得多不多、额度够不够，否则降级路径只在出事那天才被发现。
- **内容签名代替事件总线做缓存失效**：缓存条目带一份知识库文本的 SHA-256 前 16 位（`AiService.java:78,468-480`），取缓存时先比签名，不一致就在 `synchronized` 里重建（`:328-346`）。业务模块之间因此不需要任何通知机制，新增一个会改知识库的模块也不用记得清缓存；代价是"改没改"要等下一次请求才知道，适合读多写少、重建成本可接受的场景。
- **文档里有日期，prompt 里就要有当前日期**：system prompt 注入今天，并写死推断规则（`AiService.java:493-500`），规定日期已过就不能顺着原文的"预计"字样回答。任何拿简历、合同、招生计划这类带绝对时间的文本做问答都会撞到同一条：模型会照抄原文的时间措辞，而这类错误只在被真实提问时才暴露。
- **没有分词库时的中文检索兜底**：问题拆成英文词 + 中文 2 字/3 字滑窗 gram，先过一遍单字停用词表，再按 token 长度给命中计分（`AiService.java:722-799,815-827`），最后按"每栏最多 2 行、总共最多 6 行"截断。滑窗 gram 是这里真正的通用件——不依赖词典、不会漏专名，代价是噪声 token 多，所以要靠栏目配额而不是纯分数截断。
- **多轮上下文放在服务端**：只按会话键从库里回捞最近 6 条再复原正序拼消息（`AiService.java:505-515`），前端只负责存住并回传这个 id（`AiChatWidget.vue:124-132`）。前端传历史的做法会被长度上限和篡改问题反复拖累，而且同一会话的上下文和审计记录天然分叉；库里既然已经逐轮落库，回捞就是免费的能力。
- **会话键要带上内容作用域**：历史表没有版本列，会话键就写成 `sessionId + "#" + versionId`（`AiService.java:112-115`），一行拼接把「同一浏览器换简历版本后旧上下文继续进 prompt」这条路断掉，比给表加列省掉一次迁移（建表是 `CREATE TABLE IF NOT EXISTS`，加列对已有库不生效）。两个容易漏的点：拼好之后要**先截主键再拼后缀**，否则后缀可能正好被列宽截掉、隔离静默失效；而且这类作用域只能由服务端拼——默认版本是服务端解析出来的，前端在「跟随默认」的链接下根本不知道当前版本号。
