# 11 数据库设计

12 张表，全部建在 `backend/src/main/resources/schema.sql`，示例内容在仓库根目录那份 `resume_seed.sql`（真实简历，不入库、也不放 resources，见 `.gitignore:30-34`），没有 XML mapper、没有 flyway/liquibase。建表脚本每次连接都会执行，所以语句全部写成幂等形式；示例内容不在这里灌，由 `init/DataInitializer.java:69-86` 在空库时导入一次。这一篇按三组表过一遍字段与约束的取舍，再解释 JDBC URL 上那串参数的作用，最后记录几处「看着别扭但是有原因」的地方。

## 三组表

```
resume_version ─┬─ profile      (1:1，每版本一条)
                ├─ education    (1:N)
                ├─ experience   (1:N，工作与项目共用)
                └─ skill        (1:N，按 category 分组)

honor / portfolio ── 按 owner_name 归档，不挂版本

user · site_config · share_link · visit_log · ai_chat_history ── 运行期数据
```

分组依据是「换一份简历方向时这些数据要不要跟着变」。左侧四张跟版本走，中间两张跟人走（同一人的荣誉证书和作品集在所有版本里共享），右侧五张和简历内容无关。

## H2 的连接参数

`application.yml:18` 的 URL 拆开来是六段（`application-prod.yml:12` 完整重复了一遍同样的串）：

| 片段 | 作用 |
|------|------|
| `jdbc:h2:file:${H2_DATA_DIR:./data/resume}` | 文件模式，数据落在 `resume.mv.db`。不是内存模式，重启不丢 |
| `MODE=MySQL` | MySQL 兼容模式：反引号、`AUTO_INCREMENT`、`LIMIT`、`DATE()` 这些写法都能用 |
| `DATABASE_TO_LOWER=TRUE` | 标识符统一小写，和 `schema.sql` 里的小写表名列名对齐 |
| `DEFAULT_NULL_ORDERING=HIGH` | NULL 排序时视为最大。这一项和第 03 篇的 `is_default` 唯一约束无关，只是给 `ORDER BY 可空列` 定顺序 |
| `NON_KEYWORDS=USER` | 把 `user` 从保留字里摘出来，否则 H2 2.x 里 `CREATE TABLE user` 直接报错，表名要写成 `"USER"` |
| `INIT=RUNSCRIPT FROM 'classpath:schema.sql'` | 每次连接执行建表脚本；语句幂等，表已存在时等于什么都不做 |

`NON_KEYWORDS=USER` 和 `INIT` 是最容易踩的两处：前者省掉了改名（改成 `admin_user` 之类）；后者属于 H2 驱动层参数，没有「只在首次连接执行」的开关，INIT 里写什么语句就每次连接都跑一遍。所以 `schema.sql` 里的 12 条建表和 11 条索引全部带 `IF NOT EXISTS`，脚本开头也不写 `DROP TABLE`——一旦落下 DROP，每次重启都会先删表再建，运行期数据全清。幂等之后 INIT 的真实含义才回到「首次建库」：表已经存在时整份脚本是无操作，`.mv.db` 里的内容原样留着。

`INIT` 只挂建表脚本，示例内容不在这里灌。H2 的 `RUNSCRIPT` 没法表达「数据为空时才执行」，这一步放在 Java 侧：`versionMapper.selectCount(null)` 为 0 才用 `ScriptUtils` 跑 `data.sql`（`init/DataInitializer.java:69-86`），细节和验证过程写在第 10 篇。

另外 `NON_KEYWORDS` 只影响 URL 里声明的表名；新增表时如果撞上 H2 保留字（`value`、`key`、`year` 之类），要么加进这个列表，要么改列名。

## 表结构

### resume_version（`schema.sql:86-95`）

| 字段 | 类型 | 约束 |
|------|------|------|
| id | bigint | PK, AUTO_INCREMENT |
| version_name | varchar(100) | NOT NULL |
| description | varchar(500) | |
| is_default | tinyint | UNIQUE（约束未命名，`:94`） |
| create_time / update_time | datetime | DEFAULT CURRENT_TIMESTAMP |

`is_default` 用「唯一约束 + 允许 NULL」来表达「最多一个默认版本」：非默认行存 NULL，H2 按 SQL 标准认为 NULL 之间互不相等，所以多行 NULL 合法；值 1 只允许出现一次。对应实体字段是 `Integer`（`entity/ResumeVersion.java:31`），刻意不用 `Boolean`，因为 `false` 会被写成 0，而 0 参与唯一约束会让第二条非默认记录插入失败。

代码里没有依赖 `DEFAULT_NULL_ORDERING` 来实现这个语义，那参数只影响排序。切换默认版本是「先把原默认行置回 NULL，再给新行写 1」两步在一个事务里完成（`service/VersionService.java:190-205`），置空那步必须用 `LambdaUpdateWrapper.set()` 显式赋值——`updateById` 会忽略实体里的 null 字段，见第 03 篇。

### profile（`:67-84`）

一个版本一行。`version_id bigint NOT NULL DEFAULT 1`，联系方式拆成 `email / phone / wechat / github / gitee / csdn` 六个独立列，另有 `name / job_title / slogan / avatar / address / about` 和 `update_time`。

没有 `create_time`——这张表只有「当前状态」，历史由版本承载。拆列而不是存 JSON：查询和后台表单都是一一对应，不需要 Jackson 类型处理器；将来要加 LinkedIn 就是加一列。

`name` 同时是 honor / portfolio 的归属键（`honor.owner_name`、`portfolio.owner_name`），这是全项目唯一一处「靠字符串关联」的关系。改姓名等于换了一个归属人，旧名字的荣誉和作品会立即从页面上消失（第 03 篇有对应的显隐后果）。

### education（`:16-27`）

`version_id`、`school`、`major`、`degree`、`start_date`、`end_date`、`description`、`sort int NOT NULL DEFAULT 0`。`end_date` 为 NULL 表示至今，前端渲染成「至今」文案。

### experience（`:29-41`）

工作和项目共用一张表，靠 `type tinyint DEFAULT 1` 区分（1 工作、2 项目）。`company` 在项目语境下是项目名，`position` 是角色，`tech_stack varchar(500)` 是项目常用字段。

合表而不是拆两张：十个字段里九个重合，拆开只为了一个 `tech_stack` 不值得，前端还要合并两次请求。代价是列名语义随 type 漂移（`company` 装项目名），这个歧义靠前端 tab 和文档消化。

### skill（`:122-130`）

`version_id`、`category varchar(50)`、`name varchar(50)`、`level int DEFAULT 80`、`sort`。一条技能一行，分组靠 `category` 字符串聚合，前端 `Map` 保序渲染（第 06 篇）。没有把分组存成 JSON 数组，理由和 profile 一样。

### honor（`:43-54`）/ portfolio（`:56-65`）

两张表都以 `owner_name varchar(50) NOT NULL` 为归属键，没有 `version_id`。honor 有 `title NOT NULL`、`image`、`issuer`、`level`、`honor_date`、`description`、`sort`；portfolio 有 `title`、`cover`、`url`、`description`、`sort`。

`image` / `cover` 存的是访问路径而不是二进制，上传落盘的机制在第 05 篇。两张表的读取排序口径一致：`sort` 升序再按 `id` 升序（`service/HonorService.java:39-42`、`service/PortfolioService.java:44-47`），AI 问答拼知识库时用的是同一套次序（`service/AiService.java:214-217,228-231`）。五张内容表的排序口径汇总在第 03 篇。

### share_link（`:97-111`）

`token varchar(64) NOT NULL UNIQUE`（`:110`）、`remark`、`version_id`（可空，空表示跟随默认版本）、`expire_time`、`max_views`、`view_count int NOT NULL DEFAULT 0`、`enabled tinyint NOT NULL DEFAULT 1`、`last_view_time`、`last_view_ip`、`create_time`。

「过期」「次数用完」都不落状态字段，判定时看 `expire_time` 与 `max_views` 比较，因此不需要定时任务。吊销是 `enabled=0` 的软删除，历史记录还在。计数用条件 UPDATE 保证并发下不超卖（`mapper/ShareLinkMapper.java:16-21`，第 02 篇）。

### visit_log（`:143-152`）

`ip varchar(64)`、`user_agent varchar(500)`、`referer varchar(500)`、`path varchar(255)`、`session_id varchar(64)`、`visit_time datetime DEFAULT CURRENT_TIMESTAMP`。

字段就这六个——不挂 `share_link_id`、不挂 `version_id`。加上之后能做「哪个链接带来多少访问、哪个版本看得多」，但当前统计面板（第 09 篇）只按天、来源、IP 三个维度出图，加了列也没人查，所以先不加。IP 和 UA 原样明文存储，后台活跃 IP 表直接展示，没有脱敏。

### ai_chat_history（`:6-14`）

`session_id varchar(64)`、`question text`、`answer text`、`source varchar(20) DEFAULT 'local'`、`create_time`。`source` 用来区分大模型回答与本地降级回答（`llm` / `local`），后台列表据此打标签。

表里没有版本列，多轮上下文的跨版本隔离落在会话键本身：落库的 `session_id` 形如 `sessionId#versionId`，后缀就是这一轮回答所用的简历版本，因此「按会话取多轮历史」这条索引天然只会命中同一版本的记录（口径与拼法见第 04 篇）。列宽 64 也正因为要留出后缀，写入前是先截主键再拼后缀。

### site_config（`:113-120`）

四列：`site_title`、`default_theme`、`ai_enabled tinyint NOT NULL DEFAULT 1`、`update_time`，`id bigint NOT NULL` 是普通主键（不是自增）。

单例表的两个约定：`entity/SiteConfig.java:21` 用 `@TableId(type = IdType.INPUT)` 关掉自增（全局默认是 `id-type: auto`，`application.yml:40-42`），读写都是 `selectById(1)` / `updateById`，`service/SiteConfigService.java:15` 把 `CONFIG_ID = 1L` 固定下来，查不到就返回内存里的默认值而不抛异常（`:22-28`）。`:25,29` 给 `siteTitle` 和 `defaultTheme` 标了 `updateStrategy = FieldStrategy.IGNORED`，使这两个字段能被显式更新为 NULL（清空标题）。`aiEnabled` 没有加这个策略，因此传 null 会被 MyBatis-Plus 默认的「非空才更新」忽略，正好符合「开关不该被清空」的期望。

### user（`:132-141`）

`username varchar(50) NOT NULL UNIQUE`、`password varchar(100)`（BCrypt 密文）、`nickname`、`avatar`、`create_time`。实际一行，初始脚本的种子记录里存的是密文而非明文口令（口令值不在笔记里写，那份脚本本身也不入库）。H2 里的 `password` 不是保留字，不需要额外加进 `NON_KEYWORDS`。

## 索引

`schema.sql:154-164` 一共 11 个二级索引：

| 索引 | 表(列) | 支撑的查询 |
|------|--------|-----------|
| `idx_ai_session` | ai_chat_history(session_id) | 按会话取多轮历史 |
| `idx_ai_create_time` | ai_chat_history(create_time) | 后台按时间倒序分页 |
| `idx_education_version` | education(version_id) | 版本内查询 |
| `idx_experience_version_type` | experience(version_id, type) | 版本 + 工作/项目筛选 |
| `idx_honor_owner` / `idx_portfolio_owner` | honor / portfolio(owner_name) | 按归属人取全部 |
| `idx_profile_version` | profile(version_id) | 版本内取一行 |
| `idx_skill_version` | skill(version_id) | 版本内查询 |
| `idx_share_enabled` | share_link(enabled) | 有效链接列表 |
| `idx_visit_time` | visit_log(visit_time) | 趋势、时间范围统计 |

`share_link.token` 没有单独建索引——第 110 行的 `UNIQUE (token)` 自带唯一索引，验证链接时按 token 查是走索引的。`resume_version.is_default` 同理。

## 几处「看着别扭但是有原因」的写法

**没有外键约束。** 版本删除时靠代码显式级联（`service/VersionService.java:206-221`，先删 education / experience / skill / profile 再删版本记录）。省掉外键换来的是不用关心删除顺序引起的约束冲突，也没有跨表锁；风险是任何绕过服务层的直接 SQL 写入都可能留下孤儿行。

**没有乐观锁、没有逻辑删除。** 全项目没有 `@Version`、没有 `@TableLogic`，实体就是普通 `@Data` + `@TableName`。并发写冲突在这个访问量级不构成问题，删除都是物理删。

**`update_time` 靠 Java 侧填充，不靠 DDL。** 建表语句里所有时间列只写 `datetime DEFAULT CURRENT_TIMESTAMP`（`schema.sql:91-92` 是最典型的一例），全文件没有任何 `ON UPDATE CURRENT_TIMESTAMP`。修改时真正推进时间戳的是 `config/MyBatisFillConfig.java`：一个 `MetaObjectHandler`，`insertFill` 和 `updateFill` 都往 `updateTime` 写 `LocalDateTime.now()`（`:17-25`），生效范围只限标了 `@TableField(fill = FieldFill.INSERT_UPDATE)` 的三个字段（`ResumeVersion.java:35-36`、`Profile.java:68-69`、`SiteConfig.java:35-36`）——类注释把这一点讲得很明白（`MyBatisFillConfig.java:9-13`）：新增带 `update_time` 的实体时漏掉填充注解，那一列就会退回「永远等于创建时间」的行为。

只改 SQL 加 `ON UPDATE` 是不够的：MyBatis-Plus 的 `updateById` 会把实体里读出来的旧 `update_time` 显式写回 SET 子句，数据库看到显式值就不会触发自动更新。这就是填充放在 Java 侧的原因。

**SQL 日志走 slf4j，级别可控。** `application.yml:35-39` 配的是 `log-impl: org.apache.ibatis.logging.slf4j.Slf4jImpl`，注释记录了为什么不选 `StdOutImpl`：后者绕过日志框架，把语句和参数无条件写进标准输出。现在的行为是 SQL 由 `logging.level.com.example.resume` 决定——本地 debug（`application.yml:105-108`）打印，容器里 prod 默认 info（`application-prod.yml:25-28`）不打印，需要排查时设 `LOG_LEVEL=debug` 临时打开。问答文本、访问 IP 这类内容都在 SQL 参数里，默认级别不输出也就不会整份落进容器日志。

**初始数据是一份独立脚本，而且刻意不放进构建路径。** 根目录那份 `resume_seed.sql` 按表名排序写成 12 段 `INSERT INTO`，每条记录都带显式主键，子表的 `version_id` 因此能和父记录对上。这份脚本不在 JDBC URL 的 INIT 里——INIT 每建立一条物理连接就跑一遍，带显式主键的 INSERT 放那里，第二条连接就会把同一批主键再插一次。导入时机交给 Java 侧判定：`resume_version` 计数为 0 才执行一次（`init/DataInitializer.java:69-86`），判据选版本表而不是内容子表，理由是「有没有人在用这套库」最直接的证据就是有没有版本记录。脚本挪出 `src/main/resources` 并写进 `.gitignore:30-34` 的排除项：内容就是真实简历——姓名、联系方式、管理员口令的密文、有效链接的 token 都在其中，留在 resources 就会被 `mvn package` 打进 jar，等于把简历打进镜像。代价是克隆之后的全新环境和打包产物都没有示例内容，导入那步会因为类路径资源缺失而跳过（`DataInitializer.java:74-78`），由兜底逻辑建出默认版本；要灌一次示例数据，需要手工把这份脚本复制成 `src/main/resources/data.sql`，第 10 篇有这条边界。第 03、04 篇提到版本名或归属人时，只说明内容来自这份本地脚本，既不抄内容也不给行号——行号指向仓库外的文件无法核对，而脚本里的值换人使用时全要替换。

## 可复用点

- **「最多一个 X」用唯一约束 + NULL，不加布尔列**：`is_default tinyint` 配表级 `UNIQUE (is_default)`（`schema.sql:86-95`），非默认行写 NULL、默认行写 1，数据库层就保证不会出现两条默认。三个必须一起成立的条件：实体字段类型要能装 NULL（`Integer` 而不是 `Boolean`，`entity/ResumeVersion.java:31`）；写入路径上只允许出现 NULL 和 1；把已有默认改成 NULL 要用 `LambdaUpdateWrapper.set()` 显式赋值，`updateById` 会忽略 null（`VersionService.java:198-200`）。这套写法不校验历史数据，所以读侧要留兜底链处理"零个/多个默认"（`:82-100`）。换到 MySQL 时 `UNIQUE` 对 NULL 的行为与 H2 一致（InnoDB 允许多行 NULL），不需要改。
- **单例表 = 固定主键 + 读不到不抛异常 + 字段级更新策略**：`@TableId(type = IdType.INPUT)` 关掉自增（`entity/SiteConfig.java:21`），服务里把 `CONFIG_ID = 1L` 写死（`service/SiteConfigService.java:15`），查不到就返回内存默认值而不是抛错（`:22-28`）——配置类表在空库里也该能读出可用值。同一张表上还能按字段区分「允许清空」和「不允许清空」：`siteTitle` / `defaultTheme` 标 `updateStrategy = FieldStrategy.IGNORED`（`entity/SiteConfig.java:25,29`）才能被显式更新为 NULL，`aiEnabled` 不标，传 null 就被默认的「非空才更新」忽略。注意这个枚举名字是反直觉的，`IGNORED` 指的是忽略 null 检查。
- **可空时间戳要填在 Java 侧，别指望 DDL**：建表语句全文件只用 `DEFAULT CURRENT_TIMESTAMP`，没有一处 `ON UPDATE CURRENT_TIMESTAMP`；真正推进修改时间的是 `MetaObjectHandler`（`config/MyBatisFillConfig.java:17-25`）。原因是 MyBatis-Plus 的 `updateById` 会把实体里读出来的旧值显式写进 SET 子句，数据库看到显式值就不触发自动更新——这一条对任何走 ORM 更新的项目都成立，加 DDL 只是徒劳。生效范围只限标了 `@TableField(fill = FieldFill.INSERT_UPDATE)` 的字段（三处：`ResumeVersion.java:35-36`、`Profile.java:68-69`、`SiteConfig.java:35-36`），新增带 `update_time` 的实体时漏掉注解，那一列会静默退化成"永远等于创建时间"，这是最容易漏的一环。
- **兼容模式与保留字一次性配好，省掉全库改名**：`MODE=MySQL` 让反引号、`AUTO_INCREMENT`、`LIMIT`、`DATE()` 都可用（`application.yml:18`），注解 SQL 里的 `DATE(visit_time)`、`COALESCE/NULLIF` 才不至于绑死 H2；`NON_KEYWORDS=USER` 把 `user` 从保留字里摘出来，避免改成 `admin_user` 这种牵连全库的改名。代价写在配置里：新增表或列撞上 H2 保留字（`value`、`key`、`year` 之类）要么加进这个列表，要么改列名——这条约束在写迁移脚本前就要检查一遍，别等建表报错再回来改 URL。
- **建库脚本写成幂等，灌数据前先判空库**：连接串带 `INIT=RUNSCRIPT` 时，H2 没有「只跑首次」的开关，脚本里每一条语句都会被反复执行，所以建表和建索引一律 `IF NOT EXISTS`、开头不写 `DROP TABLE`（`schema.sql:1-4` 把这条约定写在文件头）。示例数据从 INIT 里摘出来，改成应用启动时用「关键表计数为 0」判断要不要导入（`init/DataInitializer.java:69-86`），导入走 Spring 的 `ScriptUtils.executeSqlScript`，字符串里带分号也能正确切句，打进 fat jar 照样读得到。这套拆法换来的是：重启、容器自动拉起、连接池扩容都不再动运行期数据，而全新环境依然一条命令起库。坑在判据的覆盖面——只看一张表就意味着「把那几张记录手工删光」会被视为空库重新灌一遍；而示例数据属于个人内容、被排除在仓库和构建路径之外时，全新克隆走的是「资源不存在就跳过导入」那一支，两种边界都要写进注释。
- **列和索引只服务已有查询，不留预留**：`visit_log` 只有六个字段，不挂 `share_link_id`、不挂 `version_id`（`schema.sql:143-152`），因为出图维度只有天 / 来源 / IP 三个（第 09 篇）；11 个二级索引逐条对应一个真实查询（`:154-164`），`token` 与 `is_default` 不重复建索引，靠 `UNIQUE` 自带（`:94`、`:110`）。同一条判断也决定了 honor / portfolio 用 `owner_name` 字符串关联而不建外键，以及全库没有外键约束、没有 `@Version`、没有 `@TableLogic`——级联删除写在代码里换取删除顺序自由和跨表锁的缺席（`VersionService.java:206-221`）。要迁移到多人写入或有审计要求的场景时，这套取舍正好是要重新评估的清单：孤儿行、并发超卖、软删除历史三件事都得补。
