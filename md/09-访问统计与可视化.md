# 09 访问统计与可视化

统计只有两张表参与：`visit_log` 记录访问，`ai_chat_history` 记录问答（第 04 篇）。这一篇写清「一条访问」的口径是怎么定的、上报链路上一环扣一环的去重、四个统计接口各自的算法，以及数据概览页的两个图表。

## 口径：一行不等于一次打开

`visit_log` 每行代表的是「一个会话窗口内的一次访问」，不是页面打开次数。判定发生在写入侧——写入前先查窗口内有没有记录，有就什么都不写：

```java
LocalDateTime since = LocalDateTime.now().minusMinutes(sessionWindowMinutes);
long recent = StringUtils.hasText(sessionId)
        ? visitLogMapper.countRecentBySession(sessionId, since)
        : visitLogMapper.countRecentByIp(ip, since);
if (recent > 0) return false;
```

`service/VisitService.java:36-42`。窗口大小由 `app.visit.session-window-minutes` 决定，默认 30（`application.yml:87`，可用环境变量 `VISIT_SESSION_WINDOW_MINUTES` 覆盖；`VisitService.java:29-30` 的 `@Value` 也带同样的 30 兜底）。

两套去重键的取舍：

- 有 `sessionId` 时按 session 查（`mapper/VisitLogMapper.java:27-29`）。sessionId 由前端在 localStorage 里生成并长期保留（`views/home/ResumeHome.vue:254-261`，格式 `时间戳-随机串`），同一浏览器多标签、多次进入都算同一人。
- 没有 sessionId 时退化到按 IP 查（`VisitLogMapper.java:34-36`）。同一路由器下的多个访客会被合并成一条，这是兜底路径的已知精度损失；正常前端一定会带 sessionId，只有直接 `curl` 打接口才会走到这条。

`record()` 返回 boolean 表示「本次是否真的写入」，调用方没有使用（`controller/VisitController.java:34-40`）。也就是说前端拿到的永远是成功，重复访问被忽略了也不自知——统计面板不需要实时反馈，这个返回值目前只是给日志/测试留的口子。

字段长度在写入侧截断，避免超出列宽直接报错（`VisitService.java:45-49`，`truncate` 在 `:156-161`）：user_agent 500、referer 500、path 255、session_id 64，和建表语句里的列宽一一对应（`resources/schema.sql:151-158`）。IP 不截断，列宽 64 够放 IPv6。

## 上报链路

前端在首屏配置的尾段发一次 `POST /api/visit`（`ResumeHome.vue:310-314`），带 `path` 与 `sessionId` 两个字段（`dto/VisitRequest.java:14,18`）。请求体是 `@RequestBody(required = false)`（`VisitController.java:30`），空 body 也能过，此时 path 和 sessionId 都是 null，走 IP 兜底分支。

其余三个来源字段全部服务端取（`:35-37`）：`IpUtils.getClientIp(request)`、`User-Agent` 头、`Referer` 头。IP 的多级取值顺序和 Nginx 反代下必须配 `X-Real-IP` / `X-Forwarded-For` 这件事在第 02 篇写过，这里只补一句：`ip` 字段拿不到真实客户端 IP 时，所有 IP 兜底去重和「活跃 IP」榜单都会失真。

前端这一侧还有一层标签页级抑制：`sessionStorage['resume-visit-reported']` 一旦置位，本标签页内刷新、HMR、路由跳转都不再上报（第 06 篇）。所以是三层叠加：sessionStorage 挡重复请求 → sessionId 挡同浏览器跨会话重复 → 会话窗口（默认 30 分钟）挡跨标签页重复。

上报接口不是匿名的：`POST /api/visit` 要求 `ROLE_ADMIN` 或 `ROLE_VISITOR`（`SecurityConfig.java:76-79`，第 02 篇的权限表），也就是说脚本得先拿一条有效专属链接换到访客令牌才刷得动。刷不出脏数据靠的是窗口去重；真要防住持令牌刷量的情况，需要在 `VisitController` 上加限流，目前那里没有（第 02 篇的限流器只挂在专属链接换取入口）。

## 四个统计接口

`controller/StatsController.java:23` 前缀 `/api/admin/stats`，全部要 JWT：

| 路径 | 参数 | 返回键 | 实现 |
|------|------|--------|------|
| `GET /overview` | — | `totalVisits` / `uniqueVisitors` / `todayVisits` / `todayUniqueVisitors` / `sessionWindowMinutes` | `VisitService.java:55-67` |
| `GET /trend` | `days`，默认 7，钳到 1~90（`:39-42`） | `date` / `visits` / `uniqueVisitors` | `:72-94` |
| `GET /sources` | — | `source` / `count` | `:99-118` |
| `GET /top-ips` | `days`，同样钳 1~90（`:55-58`） | `ip` / `count` | `:120-131` |

没有独立的 StatsService，四个方法都写在 `VisitService` 里，控制器直接注入 `VisitService`（`StatsController.java:27`）。聚合 SQL 全部用 `@Select` 注解在 Mapper 接口上（`VisitLogMapper.java:21-78`），项目没有 XML mapper。

**总览**（`VisitService.java:55-67`）：

- `totalVisits` 用 `visitLogMapper.selectCount(null)`——BaseMapper 的全表计数，统计的是「窗口去重后的行数」，所以这个数不是原始 PV。
- `uniqueVisitors` 用 `COUNT(DISTINCT ip)` 全历史去重（`VisitLogMapper.java:21-22`）。
- 今日两项以 `LocalDate.now().atStartOfDay()` 为界（`:56,60-63`），今日访问同样是行数口径。
- `sessionWindowMinutes`（`:65`）把去重窗口原样透出，前端指标卡的文案用这个数拼句子，配置一改文案跟着变。

**趋势**（`:72-94` + `VisitLogMapper.java:46-55`）：SQL 只按 `DATE(visit_time)` 聚合出有访问的日期，别名 `d/c/u`；补零在 Java 侧做——先 `Map<LocalDate, row>`，再按 `today.minusDays(days - 1 - i)` 逐日生成 `days` 条记录（`:84-92`）。补零放在 Java 而不是 SQL，是因为 H2 里造日期序列要写递归 CTE，Java 循环更短也更好读。`toLocalDate`（`:143-154`）兼容 `LocalDate` / `java.sql.Date` / `java.util.Date` / 字符串四种回传形态，这是不同 JDBC 驱动对 `DATE()` 返回类型不一致的兜底。

**来源**（`:99-118` + `VisitLogMapper.java:58-66`）：SQL 里 `COALESCE(NULLIF(TRIM(referer), ''), '直接访问')` 把空来源归一类，`ORDER BY c DESC LIMIT 20`。Java 再用 `extractHost`（`:133-141`，`URI.create(...).getHost()`，解析失败原样返回）把同一站点不同页面的 referer 归并成域名，`merge` 累加后按次数降序输出。

这里有个口径上的已知偏差：先 `LIMIT 20` 再归并。若某域名的 30 个不同来源页各带来 1 次访问，这些行排在第 20 名之后就在 SQL 层被砍掉了，归并阶段也无从累加——长尾来源的占比会被低估。保留 referer 原始明细优先，饼图看的是头部来源分布，这个数量级下偏差不影响判断。

**活跃 IP**（`:120-131` + `VisitLogMapper.java:69-78`）：Top N 的数量写在 Java 里（`visitLogMapper.topIps(since, 10)`，`:122`），控制器只暴露 `days`，所以榜单固定 10 条。

## 数据概览页

`views/admin/Dashboard.vue` 四个接口并行拉（`:201-207`）：

```js
onMounted(async () => {
  await nextTick()
  trendChart = echarts.init(trendChartRef.value)
  sourceChart = echarts.init(sourceChartRef.value)
  await Promise.all([loadOverview(), loadTrend(), loadSources(), loadTopIps()])
  window.addEventListener('resize', handleResize)
})
```

`echarts.init` 必须在 `nextTick` 之后——容器 `<div>` 要有实际尺寸，否则初始化出来是 0×0 的画布。全量导入用 `import * as echarts`（`:83`），没有按需注册 chart/component，包体积换开发便利，个人站点可接受。卸载时 `onBeforeUnmount` 移除监听并 `dispose()` 两个实例（`:209-213`），`handleResize` 手动调两次的 `resize()`（`:196-199`）——ECharts 不会随窗口自动重绘。

**趋势图**是折线 + 柱状组合（`:136-166`）：`xAxis.type: 'category'` 且 `boundaryGap: false`，日期取 `d.date.slice(5)` 只留 `MM-DD`；访问次数走 `line` + `smooth` + `areaStyle: { opacity: 0.15 }`，独立访客走 `bar` + `barMaxWidth: 18` + 顶部圆角。`yAxis.minInterval: 1` 保证计数图不会出现 0.5 这样的刻度。切换 7/15/30 天用 `el-radio-group` 绑 `days` 并 `@change="loadTrend"`（`:22-26`），只重刷趋势图，活跃 IP 表固定 7 天（`loadTopIps()` 里写死 `getStatsTopIps(7)`，`:192`）。

**来源图**是环形饼图（`:171-188`）：`radius: ['42%', '68%']` 两值即环形、`center: ['50%', '44%']` 上移给底部 legend 让位，`label: { show: false }` 常态不显示标签、只在 `emphasis` 时显示，`legend.type: 'scroll'` 应对来源多时溢出。空数据时塞一条兜底项 `{ name: '暂无数据', value: 1, itemStyle: { color: '#e2e8f0' } }`（`:185`）——饼图没有数据就是一片空白，加一条灰色扇区至少让容器不显得坏掉。

四张指标卡的解释文案写在 `card.tip` 里，鼠标悬停 label 时通过 `:title` 显示（`:10`，卡数据在 `:106-117`）。文案里的会话窗口分钟数不写死：`syncCards()` 用 `/overview` 返回的 `sessionWindowMinutes` 拼出「同一访客在 N 分钟会话窗口内…只计一次」和「今日 0 点起的会话访问次数（N 分钟去重）」两句（`:119-123`），改 `app.visit.session-window-minutes` 之后后台说明跟着变（`application.yml:87`）。

活跃 IP 表直接把原始 IP 明文列出（`:44-48`），没有任何掩码或聚合。后台只有站长一人可见，但 IP 属于可识别访客的信息，`visit_log` 也是原样存储（`schema.sql:151-158`）。另外这张表没有任何清理机制——没有定时任务、没有后台删除入口，长期运行只会一直增长，唯一索引是 `idx_visit_time` 和 `idx_visit_ip`（`schema.sql:171-172`），清理得手工执行 SQL。

## 可复用点

- **去重放在写入侧，不放在读取侧**：`record()` 先查窗口内有无记录，有就一条都不写（`VisitService.java:36-42`）。读侧去重（每次查询都 `COUNT(DISTINCT session_id)`）会把口径压给每个统计接口，四个接口就得各写一遍 distinct 逻辑，且历史明细无限增长；写侧去重之后表里一行就是一次访问，`selectCount(null)` 直接是指标值。代价是明细丢了——想改成别的窗口只能重新积累。适用条件是"只要趋势，不做审计"。
- **三层抑制各挡一类重复，缺一不可**：`sessionStorage['resume-visit-reported']` 挡本标签页的刷新与 HMR；localStorage 的 `resume-sid` 让同一浏览器多标签归并（`ResumeHome.vue:254-261`）；服务端会话窗口挡跨设备同 IP 与跨标签的重复（`VisitService.java:36-42`）。前两层是省流量，第三层才是口径。写埋点时若只有前端标记，换浏览器就翻倍；若只有服务端窗口，每次刷新都白打一次接口。
- **影响口径的参数随指标一起返回**：`sessionWindowMinutes` 出现在 `/overview` 的返回体里（`VisitService.java:65`），前端指标卡的解释文案用这个数拼句子（`Dashboard.vue:119-123`），注释直接写明"窗口时长由后端返回，文案不写死配置值"。改 `app.visit.session-window-minutes` 后后台说明自动跟上。凡是"算法参数决定数字怎么读"的指标（去重窗口、统计时区、四舍五入位数、货币单位）都适用：参数是接口契约的一部分，别让前端硬编码一份副本。
- **时间序列补零放 Java，日期类型兼容写全**：SQL 只聚合出有访问的日期，缺日由 `for (int i = 0; i < days; i++)` 逐日生成（`VisitService.java:84-92`），避免在 H2/MySQL 里各写一套递归 CTE；`toLocalDate` 兼容 `LocalDate` / `java.sql.Date` / `java.util.Date` / 字符串四种回传形态（`:143-154`），这是不同 JDBC 驱动对 `DATE()` 返回类型不一致的必要兜底。同一段兜底思路还体现在写入侧的字段截断（`:45-49` + `truncate`，`:156-161`）：user_agent、referer、path、session_id 按列宽截短，让"超出列宽"这种错误不会打断上报链路——统计接口宁可存一条被截断的明细，也不要返回 500 让前端以为埋点失败。
- **图表的两处手工成本和一处空数据技巧**：`echarts.init` 必须在 `nextTick` 之后，容器有实际尺寸才不会出 0×0 画布；卸载要 `dispose()`、窗口变化要手动 `resize()`，ECharts 不自动重绘（`Dashboard.vue:201-213,196-199`）。饼图空数据时塞一条灰色兜底扇区 `{ name: '暂无数据', value: 1 }`（`:185`），容器不会显得坏掉；`yAxis.minInterval: 1` 防出现 0.5 次这样的刻度。另一处是长尾口径：来源统计先 `LIMIT 20` 再按 host 归并（`VisitLogMapper.java:58-66` + `VisitService.java:99-118,133-141`），同一域名多个来源页的访问会在 SQL 层被砍掉，长尾占比低估。要看头部分布这样够用；要算准占比，得在 SQL 里先 `GROUP BY` 归并后的 host 再 `LIMIT`——这条改法涉及 SQL 表达式，动手前要先确认 H2 支持所选的 host 提取写法。
