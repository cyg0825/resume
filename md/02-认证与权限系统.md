# 02 认证与权限

两套身份共用一条过滤器链：管理员用用户名密码换长期令牌，访客用专属链接换只读令牌。后端全程无 Session，前端在 axios 拦截器里决定带哪个令牌。

## JWT 在本项目里的形态

三段式结构、HS256 对称签名，密钥从配置项 `app.jwt.secret` 注入（环境变量 `JWT_SECRET`，`backend/src/main/resources/application.yml:70`）。密钥在 `@PostConstruct` 里构造：

```java
// security/JwtUtil.java:34-37
@PostConstruct
public void init() {
    this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
}
```

`Keys.hmacShaKeyFor` 对 HS256 有硬约束：密钥不足 32 字节直接抛 `WeakKeyException`，且异常发生在 Bean 初始化阶段，报错信息不指向密钥长度。占位默认值因此按 32 字节以上写（`application.yml:67-70` 的注释记了这个长度要求），未设 `JWT_SECRET` 也能起服务；`docker-compose.yml:12` 的兜底值同样满足这个长度约束，否则容器不带环境变量启动会在建 Bean 时失败。占位值本身不安全，部署时必须覆盖。

两类令牌的 claim 差别决定权限（`security/JwtUtil.java:42-52` 与 `:60-73`）：

| | 管理员令牌 | 访客令牌 |
|---|---|---|
| `sub` | 用户名 | `"share-" + linkId` |
| `kind` | 不写 | `"share"` |
| 其他 | `userId` | `linkId`、`versionId`（链接未绑定版本时不写这个 key） |
| 有效期 | `app.jwt.expire`，默认 5184000000 ms = 60 天（`application.yml:72`） | `app.jwt.share-expire`，同样 60 天（`application.yml:74`） |

两个有效期都只有配置一个来源：`JwtUtil.java:25-30` 的两个 `@Value` 都不带内联默认（属性在 `application.yml` 里必然有定义，写内联默认等于埋一份会过时的副本）。访客令牌不是短期令牌，有效期与管理员令牌同为 60 天；`ShareLinkController.java:35-36`、`vo/ShareAccessVO.java:17` 的文案都按这个口径写。真正让访客提前失效的不是令牌寿命，而是下面那条每次请求回查链接的规则。

解析失败（过期、签名不符、格式错误）统一返回 null 而不抛异常，只打 debug 日志（`JwtUtil.java:79-89`），所以过滤器里不需要 try-catch 包住解析。

## 过滤器做了什么

`security/JwtAuthenticationFilter.java` 继承 `OncePerRequestFilter`，真实流程有几个容易记错的细节：

1. 只认 `Authorization` 头且必须以 `Bearer ` 开头，取 `substring(7)`（`:38-40`）。
2. 当前 `SecurityContext` 里已有 Authentication 时不覆盖（`:42`）。
3. `kind=share` 时回查 `share_link` 表，判定三个条件：记录存在、`enabled == 1`、`expire_time` 为空或晚于当前时间（`:82-86`）。回查抛任何异常一律视为无效（`:87-89`）。
4. 判定不通过时**不是"清空认证信息"**，而是根本不写入 SecurityContext，然后照常 `doFilter` 放行（`:44-47`）。因为整个应用无 Session，后续落到 Security 的 401 entryPoint，效果等价于匿名请求。
5. 角色是 `ROLE_VISITOR` / `ROLE_ADMIN` 字符串直接赋（`:50-51`）；没有 `kind` claim 的令牌走 ROLE_ADMIN 分支，也就是说"是不是管理员"取决于令牌里没有 `kind=share`，而不是有 `kind=admin`。
6. principal：管理员是用户名字符串，访客是 `SharePrincipal`（`security/SharePrincipal.java:9`，一个只有 `linkId` 与 `versionId` 的 record），赋值处见 `security/JwtAuthenticationFilter.java:48-61`。

第 5 点和"吊销即时生效"是同一条因果链：访客令牌每次请求都回查数据库，管理员把链接吊销或改过期时间之后，已发出的令牌在下一次请求就失效。代价是每个受保护请求多一次 `share_link` 单行查询。

## URL 权限表

`config/SecurityConfig.java` 的匹配顺序自上而下，先命中先生效：

| 范围 | 规则 | 位置 |
|---|---|---|
| `/doc.html`、`/favicon.ico`、`/error`、`/webjars/**`、`/swagger-ui.html`、`/swagger-ui/**`、`/swagger-resources/**`、`/v3/api-docs/**` | permitAll | `:49-60` |
| `/api/auth/**`、`/api/share/access` | permitAll，未限定方法 | `:62` |
| `/uploads/**` | permitAll | `:64` |
| GET `/api/profile`、`/api/educations`、`/api/experiences`、`/api/skills`、`/api/honors`、`/api/portfolios`、`/api/config` | hasAnyRole("ADMIN","VISITOR") | `:66-75` |
| POST `/api/visit`、`/api/ai/chat` | hasAnyRole("ADMIN","VISITOR") | `:76-79` |
| `/api/admin/**` | hasRole("ADMIN") | `:81` |
| 其余 | denyAll | `:82` |

`/uploads/**` 必须公开，因为 `<img>` 不会带 Authorization 头；该路径由 `config/WebMvcConfig.java:25` 做本地目录映射，不经过 Controller。

兜底写成 `denyAll()` 而不是 `authenticated()`，新增接口时忘了配规则的结果是 401 而不是"登录即可访问"——宁可漏放行，不要漏收口。这条约定一旦破坏，多出来的入口就是访客可以写数据的入口。

文档入口的放行要写两条：`application.yml:45-48` 把 springdoc 的 UI 路径定为 `/swagger-ui.html`，而 `/swagger-ui/**` 是前缀模式，匹配不到带 `.html` 后缀的这一个具体路径，白名单里少了这一条就落进 denyAll。两条都列在 `SecurityConfig.java:50-57`（`/doc.html`、`/webjars/**`、`/swagger-ui.html`、`/swagger-ui/**`、`/swagger-resources/**`、`/v3/api-docs/**`），项目实际用的入口是 Knife4j 的 `/doc.html`。Nginx 侧对应 `frontend/nginx.conf:44-50` 的文档代理正则，覆盖的是同一组路径。

## 登录

`POST /api/auth/login`（`controller/AuthController.java:15,22`），入参两个字段都是 `@NotBlank`（`dto/LoginRequest.java:11-18`）。服务端步骤：

```java
// service/AuthService.java:23-27
User user = userMapper.selectOne(new LambdaQueryWrapper<User>().eq(User::getUsername, req.getUsername()));
if (user == null || !passwordEncoder.matches(req.getPassword(), user.getPassword())) {
    throw new BusinessException(400, "用户名或密码错误");
}
```

用户不存在与密码不匹配走同一个分支、同一句提示，避免被枚举出有效用户名。注意失败返回的是 `code=400` 且 HTTP 200（业务异常只改 body），不会触发前端拦截器里的 401 跳转逻辑，所以登录页需要自行展示错误文案。

成功返回 `LoginVO`，四个字段 `token / username / nickname / avatar`（`vo/LoginVO.java:10-13`）。`POST /api/auth/logout` 在服务端是空实现（`AuthController.java:28-31`），无状态本就没有服务端会话可销毁，登出实质是前端丢掉 localStorage 里的 token。

默认管理员由 `init/DataInitializer.java:88-99` 在 user 表为空时用 `app.admin.username` / `app.admin.password` 配置项写入，口令值不在此写出，需要时看 `backend/src/main/resources/application.yml:81-83` 的项名与环境变量覆盖名。接口描述里不写默认口令（`AuthController.java:21` 只说明令牌签发，账号来源指向配置项名）。

## 改密

`PUT /api/admin/account/password`（`controller/AccountController.java:22,30-35`），入参 `oldPassword`（`@NotBlank`）与 `newPassword`（`@NotBlank` + `@Size(min=8,max=64)`），见 `dto/PasswordChangeRequest.java:13-23`。

路径落在 `/api/admin/**` 而不是 `/api/auth/**`，是权限表决定的：`/api/auth/**` 整段 permitAll（`SecurityConfig.java:62`），挂在那下面的接口等于对匿名开放；`/api/admin/**` 已经统一 `hasRole("ADMIN")`（`:81`），新增管理接口不需要碰 `SecurityConfig`。代价是账号相关的能力分散在两个 Controller，读代码时改密不在认证那一节里。

用户名不取自请求体，取 `Authentication#getName()`（`AccountController.java:33`）。管理员令牌的主体就是用户名（`security/JwtAuthenticationFilter.java:48,54` 把 `claims.getSubject()` 直接作为 principal），因此改密只能改自己，参数里也没有可篡改的 userId。

服务端步骤（`service/AuthService.java:37-53`）：

```java
// 三次校验：账号存在、原密码匹配、新旧不同
if (!passwordEncoder.matches(request.getOldPassword(), user.getPassword())) {
    throw new BusinessException(400, "原密码不正确");
}
if (passwordEncoder.matches(request.getNewPassword(), user.getPassword())) {
    throw new BusinessException(400, "新密码与原密码相同");
}
```

写库用只带 `id` 与 `password` 的部分实体 `updateById`，MyBatis-Plus 默认忽略 null 字段，`nickname / create_time` 不受影响。改密的提示语与登录不同，这里明确说「原密码不正确」——调用方已经是登录态的管理员，不存在枚举对象，把三种失败合并反而难排查。

改完密码，已签发的 JWT 依然有效（无状态，服务端没有可销毁的会话），要立即让旧令牌失效只能等 `app.jwt.expire` 到期或换 `JWT_SECRET`（换密钥会把访客令牌一起作废）。同理，`ADMIN_PASSWORD` 配置项只在 user 表为空时生效，改过密码后重启不会把口令刷回去。

## 专属链接

访客认证的核心是一张 `share_link` 表加一个换取接口。

生成时 token 是 32 字节 `SecureRandom` 转十六进制，得到 64 个小写字符（`service/ShareLinkService.java:165-169`），与列定义 `token varchar(64) NOT NULL` 加 `UNIQUE (token)` 吻合（`schema.sql:99,110`）。链接本身形如 `/#/r/{token}`，前端拼的是 `window.location.origin`，没有硬编码域名（`views/admin/ShareLinkManage.vue:226-228`）。

一条链接可以带四个约束，都是可空即不限制：`remark`（备注，仅后台可见）、`versionId`（绑定版本，空表示跟随默认）、`expireTime`、`maxViews`。创建时校验 `maxViews <= 0` 拒绝、过期时间早于当前拒绝、绑定的版本不存在拒绝（`ShareLinkService.java:89-97`）。

换取访客令牌是 `GET /api/share/access?token=...`（`controller/ShareLinkController.java:38-39`），校验顺序严格（`ShareLinkService.java:46-71`），失败时同时给出中文提示和一个业务子码：

| 顺序 | 条件 | 失败 code 与提示 |
|---|---|---|
| 1 | token 空白 | 400 链接无效 |
| 2 | 按 token 查不到，或 `enabled != 1` | 4030 链接无效或已被吊销 |
| 3 | `expireTime` 早于当前 | 4031 链接已过期 |
| 4 | `viewCount >= maxViews` | 4032 链接访问次数已达上限 |
| 5 | 条件更新影响 0 行 | 4033 链接已失效（过期、次数用尽或被吊销） |

四个子码定义在 `ShareLinkService.java:38-41`，是前端拦截页选文案的唯一依据。历史上这里只有 `403` 一个值，前端只能拿中文提示做关键字匹配，后端改一句文案前端就退化成 `invalid`——改成按码分支后，提示文字可以随便调。子码沿用 403 的语义加一位后缀，HTTP 状态仍是 200（业务异常只改 body）。

第 4 步是 select 出来的快照判断，第 5 步才是真值。并发下两个请求同时通过第 4 步是必然的，所以自增和上限判定压在一条 SQL 里做：

```sql
-- mapper/ShareLinkMapper.java:16-21
UPDATE share_link SET view_count = view_count + 1, last_view_time = NOW(), last_view_ip = #{ip}
WHERE id = #{id} AND enabled = 1
  AND (expire_time IS NULL OR expire_time > NOW())
  AND (max_views IS NULL OR view_count < max_views)
```

受影响行数为 0 就说明这一刻已不可用。这是全项目唯一一处并发处理，没有用乐观锁，也没有 MyBatis-Plus 的 `@Version`。

返回体 `ShareAccessVO` 七个字段：`visitorToken`、`linkId`、`versionId`、`remark`、`expireTime`、`maxViews`、`viewCount`（`vo/ShareAccessVO.java:18-32`）。其中 `viewCount` 是内存里 `+1` 算出来的近似值（`ShareLinkService.java:81`），不是回查数据库的结果。

吊销是 `PUT /api/admin/share-links/{id}/disable`（`ShareLinkController.java:61`），只把 `enabled` 置 0、不删行（`ShareLinkService.java:122-131`）。真正的删除没有开放给后台，理由是已经发出去的链接一旦删行，访客请求会在"查不到记录"分支上失败，后台表格里也查不到这条历史。

反过来，Token 是可以写回的：`PUT /api/admin/share-links/{id}/token`（`ShareLinkController.java:67-74`）把已有链接的 Token 换成给定值（`ShareLinkService.java:138-160`）。需要这个入口是因为 Token 一旦发出就在别人手上，而链接记录可能被误删、也可能随数据库迁移丢掉——重新生成只会得到一串新随机值，旧地址从此作废。校验三步：格式必须 64 位十六进制（`dto/ShareTokenUpdateRequest.java:13-15`，形状与生成侧一致），落库前 `trim().toLowerCase()`（`ShareLinkService.java:143-144`，访客侧是按字符串精确匹配，大小写不一致就等于换了串），再查这个值是否已被别的链接占用（`:148-154`，`token` 列本身有唯一约束，预检只为把数据库异常换成可读提示），与当前值相同则直接返回不写库（`:145-147`）。改动范围只有 Token 一列，备注、绑定版本、访问次数、吊销状态一概不动，改完的链接统计接得上。范围边界两句：已吊销的行改了 Token 依旧无效（`accessByToken` 第二道判定的就是 `enabled`），占用检查与写入之间没有加锁，同时改两条链接撞同一个值时由唯一索引兜底。

接口入口带 IP 限流，防止有人枚举 token：`SimpleRateLimiter` 以 `"share-access:" + ip` 为键（`ShareLinkController.java:41-44`），实现是 60 秒内最多 20 次的滑动窗口：每个键一个 `ArrayDeque<Long>` 存时间戳，进队前先弹掉窗口外的（`common/SimpleRateLimiter.java:10-24`）。固定窗口/令牌桶都不是，纯粹是时间戳队列；`DEFAULT_LIMIT` 和 `WINDOW_MS` 是常量，不读配置。AI 问答接口没有接限流，全后端只有这一处使用点。

客户端 IP 的取法在 `util/IpUtils.java:14-32`：依次试 `X-Forwarded-For`、`X-Real-IP`、`Proxy-Client-IP`、`WL-Proxy-Client-IP`、`HTTP_CLIENT_IP`、`HTTP_X_FORWARDED_FOR`，跳过空白与 `unknown`，多段值取第一个逗号前段，切完还是空白就继续试下一个头，全部无效才回落 `request.getRemoteAddr()`。反代后面必须让 Nginx 传这些头，否则限流和统计拿到的都是容器内网地址。这些头都由客户端控制，本项目只用作限流键与统计口径，不作为鉴权依据。

## 前端怎么带令牌

请求拦截器管理员优先（`frontend/src/utils/request.js:11-25`）：先读 `localStorage.token`，没有才读访客令牌（key 是 `resume-share-token`，定义在 `utils/share.js:9`）。两个令牌同时存在时永远用管理员令牌，这样站长打开分享链接也能看到完整内容。

401 的三种分支（`request.js:49-68`）：

- 有管理员令牌 → 清 `token`，跳 `#/login`（已在登录页则不重复跳）。
- 只有访客令牌 → `clearShareAccess()` 清两个 key（令牌与绑定版本），跳 `#/blocked?reason=expired`。
- 都没有 → 由路由守卫拦到 `/blocked?reason=forbidden`。

路由守卫三条规则（`router/index.js:122-140`）：`/admin` 开头且无 token → 跳登录并带上 `redirect`；已登录访问 `/login` → 直接进 dashboard；`meta.requiresShare` 的页面（首页与荣誉详情）既无管理员令牌又无访客令牌 → 跳拦截页。守卫开头还会按 `meta.title` 设置 `document.title`（`:123`）。history 用 `createWebHashHistory`（`:112`），配合 Nginx 的 `try_files` 回退，刷新不会 404。

访客进入的完整链路：`/#/r/{token}` → `ShareEntry.vue:34-38` 调 `accessShareLink` → 成功后 `saveShareAccess` 写 `resume-share-token`、`resume-share-version` 两个 key → `router.replace('/')`。失败时按后端业务子码映射拦截页原因（`ShareEntry.vue:25-32`：4031 → expired、4032 → views、429 → limit、其余 invalid），900 ms 后跳转。返回体里的 `remark` 不再落 localStorage——这个字段只用于后台区分链接，前台没有任何读取方。这个接口调用带 `silentError: true`（`api/index.js:74`），错误由本页展示，不走全局提示。

防索引靠两道：`index.html:7` 的 `robots = noindex,nofollow,noarchive`，加上未认证时首页接口全部 401。

```java
// common/GlobalExceptionHandler.java:31-35 —— 这段实际不会被 URL 级授权触发
@ExceptionHandler(AccessDeniedException.class)
public Result<Void> handleAccessDenied(AccessDeniedException e) { ... }
```

URL 级拒绝发生在 Security 过滤器链，响应由 `SecurityConfig.java:93-99` 直接写 out，请求根本进不到 `@RestControllerAdvice`。这个 handler 只对方法级注解授权有意义，目前代码里没有方法级注解。

## 可复用点

- **用一次回查换即时吊销**：JWT 本身不可撤销，做法是令牌只存身份（`sub`、`linkId`），每次请求回查授权记录的有效性（`security/JwtAuthenticationFilter.java:82-89`）。吊销、改过期时间、次数用尽都在下一次请求生效。单行主键查询，量级不大就不用缓存；真需要缓存时换成「记录里放一个签发后版本号，令牌带同一个版本号比对」，同样不用改令牌结构。
- **判定不通过就不写，而不是清空**：过滤器里校验失败时不去动 `SecurityContext`，直接照常放行（`JwtAuthenticationFilter.java:44-47`）。无 Session 的架构里后续统一落到 401 entryPoint（`config/SecurityConfig.java:85-91`），响应口径由一处决定，比在过滤器里手写 401 更难写错。
- **凭证要留出「管理员改回指定值」的口子**：随机凭证（这里是 64 位十六进制 Token）一旦发出去就脱离掌控，记录被误删或数据库搬迁都会让旧地址失效，而重新生成解决不了「对方手上那串还得继续用」。做法是给后台加一条按 ID 改凭证的接口，配套四件事：格式校验用生成侧的同一形状（`@Pattern` 而不是长度判断）、入库前归一化大小写、先查唯一性再写、只改这一列其余字段不动（`service/ShareLinkService.java:138-160`）。这条口子必须锁在管理权限之下，不做成公开接口，日志里也不输出凭证值。
- **失败原因走业务子码，不走文案**：`4030/4031/4032/4033` 四个子码定义在服务层常量里（`service/ShareLinkService.java:38-41`），前端按码分支选拦截页文案（`views/home/ShareEntry.vue:25-32`）。中文提示从此只是给人看的，改文案不再牵动前端逻辑——只要一个分支依赖提示文字，这条链路迟早会坏。
- **上限内的计数用条件 UPDATE**：`UPDATE ... WHERE enabled = 1 AND (expire_time IS NULL OR expire_time > NOW()) AND (max_views IS NULL OR view_count < max_views)`（`mapper/ShareLinkMapper.java:16-21`），看受影响行数决定成败。自增和判定在同一条语句里原子完成，不需要乐观锁字段，也不需要先查后写；适用于「只增、有上限、超限即拒」这类计数。
- **错误提示合并，防枚举**：用户不存在与密码不匹配走同一分支、同一句话（`service/AuthService.java:23-27`），返回码也统一。同时把可被枚举的入口（这里是按 token 换访问权）单独挂限流（`controller/ShareLinkController.java:41-44`），限流键是客户端 IP，而 IP 头由反代传入且不作为鉴权依据（`util/IpUtils.java:14-32`）——这两个约束缺一不可，否则限流可以被伪造头绕过，或者反过来把 IP 当身份。
- **新管理接口挂在已收口的前缀下，不扩白名单**：改密落在 `/api/admin/account/password`（`controller/AccountController.java:22`）而不是语义更顺的 `/api/auth/password`，因为 `/api/auth/**` 整段 permitAll（`config/SecurityConfig.java:62`），往公开前缀上加一个写接口等于自己造洞，而 `/api/admin/**` 的 `hasRole("ADMIN")`（`:81`）已经把所有管理接口收在一条规则里。判据是「这条规则是白名单还是收口」：白名单只能少不能多，收口可以往里加。配套的两点：身份取 `Authentication#getName()` 而非请求体参数，避免出现可篡改的 userId；无状态 JWT 下改密不销毁已签发令牌，这一点写进接口描述（`AccountController.java:29`）和前端提示，不做「改完强制登出」的假动作——真要让旧令牌立即失效只有换 `JWT_SECRET`，而那会连访客令牌一起作废。
