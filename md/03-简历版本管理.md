# 03 简历版本管理

简历内容按"版本"归档：一个版本 = 一份完整简历。默认版本给访客看，管理员可以预览任意版本，专属链接可以绑定到某个版本。示例数据里两个版本的名称不在笔记里写出——那份脚本的内容就是真实简历，已被 `.gitignore:30-34` 排除、不进版本库，换人使用时内容全要替换。

荣誉证书和作品集不跟版本走，按归属人姓名归档。这是本项目唯一一处"两套归属口径并存"的设计，后面所有关于显隐、AI 知识库、导入的逻辑都受这一口径影响。

## 版本隔离的唯一入口

`service/VersionService.resolveVersionId` 是服务端决定"这次请求用哪个版本"的唯一地方，所有简历读写接口都要先过这一层。分支如下（`VersionService.java:43-66`）：

```
访客（principal 是 SharePrincipal）
  ├ 链接未绑定版本 → 忽略入参，强制 defaultVersionId()      :49
  ├ 绑定的版本已被删 → BusinessException(404, "该链接暂不可用，请联系站长更新")  :54
  └ 绑定且存在 → 只返回该 id                                :56
非访客
  ├ 入参 versionId 指定 → selectById 为 null 则 404 "指定的简历版本不存在"，否则原样返回  :60-61
  └ 未指定 → defaultVersionId()                             :65
```

访客路径从头到尾没有读入参 versionId（`:45`），所以前端拼什么参数都无效。防越权只做在服务端这一处，前端那层只是不显示入口。

访客会读到的文案里不出现「版本」字样：绑定版本被删掉时报的是「该链接暂不可用，请联系站长更新」（`:54`），而不是把「这份简历还有其他版本」这件内部事实讲给访客。同一条链路上的另一句「尚未初始化任何简历版本」（`:97`）保留原样，那只在空库首次启动时出现，站点还没有内容可暴露，这时候让站长一眼看出原因比措辞统一重要。问答侧的同一口径见第 04 篇。

判定访客身份靠 `SecurityContextHolder` 里的 principal 类型：

```java
// VersionService.java:69-75
private SharePrincipal currentVisitor() {
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    if (auth != null && auth.getPrincipal() instanceof SharePrincipal sharePrincipal) {
        return sharePrincipal;
    }
    return null;
}
```

管理员未指定版本时走默认版本，因此后台所有页面都必须显式带 versionId，否则会静默写到默认版本上去。前端的做法见第 08 篇的版本作用域组件。

## 默认版本的兜底链

理论上唯一约束保证最多一个默认标记，但历史数据可能不止一个，`defaultVersionId()`（`VersionService.java:82-100`）的处理是：恰好一个直接返回；多于一个按 `contentScore` 取最大、再按 id 取大（`:88-93`）；一个都没有则回落 `selectById(1L)`，连 id=1 都没有才抛 404（`:95-99`）。

```java
// VersionService.java:103-112 节选：完整度 = 教育 + 经历 + 技能 三表记录数之和
private long contentScore(ResumeVersion version) { ... }
```

评分只算 education / experience / skill 三张表，profile 不计入（`:105-110`），注释写明了原因：作品集与荣誉按姓名归档，不计入版本完整度（`:111`）。之所以要有这段兜底，是因为一个只有空白 profile 的版本被当成默认时，AI 问答的知识库会是空的，表现为"问什么答什么都不知道"，很难联想到是默认版本选错了。

## 表结构与"最多一个默认"

```sql
-- schema.sql:86-95 节选
is_default tinyint DEFAULT NULL,
UNIQUE (is_default)
```

H2 的 `UNIQUE` 按 SQL 标准把 NULL 视为互不相等，所以多行 NULL 可以共存、值 1 只能有一行，本地示例数据里前一条是 1、后一条是 NULL。要区分的是连接串里的 `DEFAULT_NULL_ORDERING=HIGH`（`application.yml:18`），该参数只影响 `ORDER BY` 里 NULL 排前还是排后，和唯一性无关，别当成「NULL 可重复」的依据。

表级 `UNIQUE(is_default)` 没有显式命名，约束对应的索引名由 H2 自动生成，`SHOW INDEX` 里查不到自定义名字（`VersionService.java:131-132` 的注释说明了这一点）。

实体上 `isDefault` 是 `Integer`，注释写"0 否 1 是"，但业务里非默认一律存 NULL 而不是 0（`entity/ResumeVersion.java:30-31`）。用 0 会立刻撞上唯一约束（两行 0 就冲突），这个字段能生效完全依赖"NULL 不参与唯一性"，所以写入路径上只能出现 NULL 和 1。

## 创建、克隆

`create` 带 `@Transactional(rollbackFor = Exception.class)`（`VersionService.java:126`）：

1. 新记录 `isDefault = null`（`:133`）。
2. 有 `sourceVersionId` 时克隆四张表：profile、education、experience、skill（`:138` 调用 `:153-183`）。做法是查出源记录、`setId(null)`、`setVersionId(新版本 id)`、循环单条 `insert`（`:159,170,176,182`）。没有批量 API，也没有 `saveBatch`，整个项目没有 Service 继承 MyBatis-Plus 的 `ServiceImpl`。
3. 无源版本时只插一条空白 profile（`:140-143`）。
4. 明确不克隆 honor / portfolio（`:184`）——两类数据按姓名归属，新版本只要 profile 里的姓名一致，内容自然就在。接口的 Swagger 描述与此口径一致（`VersionController.java:34-35`）。

"第一个版本自动设为默认"用 `selectCount(null) == 1` 判断（`:147`）。示例脚本预置两个版本时这条分支不会触发；全新克隆没有示例脚本（放在仓库根目录、不入版本库，也不放 resources），空库由兜底逻辑直接插一条 `is_default=1` 的默认版本（`init/DataInitializer.java:107-116`），不经过这里。因此只有把 `resume_version` 清空后再通过接口建版本才会走到这一支。

接口的 `versionName` 有 `@NotBlank` 校验（`dto/VersionCreateRequest.java:17`，配合 `VersionController.java:37` 的 `@Valid`），这是全项目唯一一处走 `MethodArgumentNotValidException` 分支的校验。

## 切默认与删除

```java
// VersionService.java:190-203
@Transactional(rollbackFor = Exception.class)
public void setDefault(Long id) {
    versionMapper.update(null, new LambdaUpdateWrapper<ResumeVersion>()
            .eq(ResumeVersion::getIsDefault, 1)
            .set(ResumeVersion::getIsDefault, null));   // :198-200
    version.setIsDefault(1);
    versionMapper.updateById(version);                  // :203
}
```

第一步必须用 `LambdaUpdateWrapper.set()` 而不能把实体的字段设成 null 再 `updateById`：MyBatis-Plus 默认策略会忽略 null 字段，那条 update 会变成"什么都不改"，于是旧默认标记还在，第二步插入新标记时直接撞唯一约束。代码在 `:195-196` 留了注释说明这件事。

两次 update 必须同事务，否则中间状态下库里没有任何默认版本，访客请求会落到 `selectById(1L)` 兜底，看着"能访问"但内容未必是预期的那份。

`delete`（`VersionService.java:206-221`）先校验存在（404）与"默认展示版本不可删除"（400），再按 education → experience → skill → profile → version 的顺序物理删除，不删 honor / portfolio（`:219`）。没用数据库外键级联，删除顺序和范围都在代码里显式写，好处是删之前能加业务校验，坏处是新增子表时容易忘记加一行 delete。

`update`（重命名与描述）没有事务注解（`:224`），只改 versionName 和 description 两列，用新建部分实体 `updateById`（`:228-232`）。`description` 想被清空成 null 靠实体上的 `@TableField(updateStrategy = FieldStrategy.IGNORED)`（`entity/ResumeVersion.java:26-27`）——注意这个策略的名字是反直觉的，`IGNORED` 表示"忽略 null 检查"，即 null 会被写进库。

## sort 字段：没有排序接口

education、experience、skill、honor、portfolio 都有 `sort int NOT NULL DEFAULT 0`。服务层不提供自动取号：create 只做 `setId(null)`，versionId 和 sort 完全取自请求体（`EducationService.java:24`、`ExperienceService.java:29`、`SkillService.java:24`）。前端表单里 sort 是一个 `el-input-number` 输入框，随保存接口一起提交（`views/admin/EducationManage.vue:68-70`），没有拖拽、也没有上移下移接口。

列表排序口径并不完全一致，排查顺序问题时按表看：

| 表 | 排序 | 位置 |
|---|---|---|
| education | sort 升 → startDate 降 | `EducationService.java:18-21` |
| experience | sort 升 → startDate 降，type 非空时才加条件 | `ExperienceService.java:19-24` |
| skill | sort 升 → id 升 | `SkillService.java:18-21` |
| honor | sort 升 → id 升 | `HonorService.java:39-42` |
| portfolio | sort 升 → id 升 | `PortfolioService.java:44-47` |

五张表的次级排序都是 id 升或 startDate 降，口径一致；改顺序只能靠改 sort 值，服务端没有拖拽接口。

## 荣誉与作品集的归属人

这两类内容用 `owner_name` 归档，前台接口收 versionId、后台接口收 ownerName，中间靠 profile 换名：`listByVersion` 先按版本查 profile 拿姓名，姓名为空或空白直接返回空列表（`HonorService.java:27-29`、`PortfolioService.java:32-34`）。

归属人在创建时必填，否则 400（`HonorService.java:48-49`、`PortfolioService.java:57-59`）。更新时服务层把 `ownerName` 置成 null 再 `updateById`（`HonorService.java:60,62`、`PortfolioService.java:69,71`），借助 MyBatis-Plus 默认忽略 null 的策略实现"归属人不可改"——改归属人等于把内容搬到另一个人名下，属于危险操作，宁可不让改。

后台需要一份「给哪个归属人加内容」的候选名单，`service/OwnerService.java` 就是为此写的：portfolio 与 honor 各做一次 `select owner_name, MAX(id) ... group by owner_name` 聚合（`:37,41`），两个来源的 MAX(id) 用 `map.merge(Math::max)` 合成"最近维护"的代理值（`:69`），先按该代理值降序输出已维护过内容的姓名，再把只在简历版本里出现过的姓名 trim + distinct 按字典序追加（`:47,52`）。暴露成 `GET /api/admin/owners`（`controller/OwnerController.java:19,26`），避免前端拼接三个数据源。

## 前端版本作用域

后台页面的版本作用域来自 `composables/useVersionScope.js`：暴露 `versions`、`currentVersionId`、`loadVersions` 三个成员（`:25`），默认选中 `isDefault === 1` 的版本，没有则取列表第一个（`:18-19`），当前选中项被删掉后自动回落默认版本（`:17`），挂载即拉列表（`:23`）。

这个 ref 不落地任何存储——文件里没有一处 localStorage 调用。切换版本只影响当前页面的组件状态，刷新回默认版本。好处是不会出现"后台停在三个月前的版本上，改了以为访客能看到"，代价是每进一个页面都要重新选一次。

`components/admin/VersionBar.vue` 是纯受控组件，只有 `modelValue` + `update:modelValue` 一对（`:30-39`），没有额外的 `change` 事件——页面侧统一用 `watch(currentVersionId)` 重新拉列表（`views/admin/EducationManage.vue:161`），组件再发一个事件只会造成同一页面两次请求。切换后既不跳转也不刷新页面；"预览该版本"用 `window.open('/#/?versionId=' + id)` 开新标签（`:41-45`）。

首页读这个参数的优先级在 `views/home/ResumeHome.vue:185-190`：先判 `isAdmin = Boolean(localStorage.getItem('token'))`，管理员才允许用 `route.query.versionId`；否则读访客令牌对应的 `resume-share-version`；都没有则 null（服务端取默认版本）。管理员预览时页面顶部有一条 `el-alert` 提示（`:51-62`），避免把预览态误当线上态。

## 可复用点

- **作用域解析只留一个入口**：「这次操作用哪个版本」全部走 `VersionService.resolveVersionId`（`VersionService.java:43-66`），访客分支从头到尾不读请求参数（`:45`）。凡是"前端不显示入口"当作的防护，服务端一定要有一条对应的判断；入口收敛成一个方法之后，新增接口只要过这层就自动继承隔离规则。
- **`UNIQUE + NULL` 表达「最多一个」**：不给 `is_default` 建布尔列，而是 `tinyint DEFAULT NULL` 加表级 `UNIQUE (is_default)`（`schema.sql:86-95`），非默认一律 NULL。约束由数据库保证，服务层只需要守住「写入路径上只出现 NULL 和 1」。前提是所用车架不把 NULL 当成要跳过的值——所以置空必须用 `LambdaUpdateWrapper.set()` 显式写（`VersionService.java:198-200`），两步更新再包进同一个事务。
- **唯一约束不能假设历史数据合规**：库里可能同时存在多个默认标记，读取侧就按业务指标挑一个（内容完整度评分，`VersionService.java:82-100`），而不是直接 `LIMIT 1` 或者抛错。这段兜底值得抄的点在于选指标的思路：出错时的表现要能被读懂——空白版本被当默认会让 AI 问答「问什么都不会」，而评分高的版本不会是空的。
- **区分「不改」和「清空」**：可空字段的清空靠实体上的 `@TableField(updateStrategy = FieldStrategy.IGNORED)`（`entity/ResumeVersion.java:26-27`），其余字段沿用默认的「null 不更新」。反过来，业务上不可改的字段（归属人）是在更新前把入参置 null，借默认策略实现（`HonorService.java:60,62`）。两种写法都依赖 MyBatis-Plus 的 null 策略，一旦全局调整 `update-strategy`，这两处行为会一起变，属于要盯的耦合点。
- **编辑态的作用域不做持久化**：版本作用域只存在于组件状态里（`composables/useVersionScope.js:18-25`），刷新回默认版本。凡是"选了作用域再编辑"的后台，把选择写进 localStorage 或 URL 都会造出"停在旧作用域上改，以为改的是线上"的事故；宁可每次进页面重新选一次。
