# 功能二：简历版本管理

## 功能概述

简历的所有内容（个人信息、教育、工作/项目经历、技能）都挂载在一个"简历版本"下。可以创建多个版本，每个版本是一份完整的简历快照。默认版本展示给访客，管理员可以后台预览任意版本，也可以把某个专属链接绑定到特定版本。

**注意**：荣誉证书和作品集是按"姓名"归档的，不跟版本绑定。一个人的多个简历版本共用同一套荣誉和作品集。

---

## 一、版本表结构（ResumeVersion）

关键字段：
- `id` ：主键
- `version_name` ：版本名称，如 "测试岗版"、"测试岗版1"
- `description` ：描述
- `is_default` ：是否默认。数据库有唯一索引保证最多只有一个版本是默认的（NULL 可以共存，1 只能有一行）
- `create_time` / `update_time` ：自动维护的时间戳

---

## 二、版本隔离机制

### 前端请求时怎么带版本

首页加载数据时调用 `/api/profile?versionId=xxx`、`/api/educations?versionId=xxx` 等。versionId 可以省略，省略时后端取默认版本。

### 后端 resolveVersionId

**文件**：`backend/src/main/java/com/example/resume/service/VersionService.java`

这是服务端强制版本隔离的唯一入口。所有简历查询接口都先调它来确定"当前请求应该用哪个版本"。

```
管理员请求：
  - 指定 versionId → 校验存在 → 使用
  - 不指定 → 取 is_default=1 的版本
  - 没有默认版本 → 退回 id=1

访客请求：
  - JWT 里 claim 带了 versionId（链接绑了版本）→ 强制用那个版本，忽略前端传的任何参数
  - JWT 里 versionId 为 null（链接跟随默认）→ 强制用当前默认版本
```

**防越权**：访客的 versionId 是后端在生成访客 JWT 时写进去的。即使访客手动改前端代码拼一个 `?versionId=999`，后端也会忽略它，仍然用 JWT 里绑定的版本。双保险：前端和后端都做了。

### 访客绑定版本后的生命周期

访客 JWT 里的 versionId 是固定的。如果管理员后来把这个版本删了，访客下次请求会收到明确错误：
> "链接绑定的简历版本已不可用，请联系站长更新链接"

---

## 三、创建版本

### 从已有版本克隆

创建新版本时可以指定 `sourceVersionId`。后端会把源版本下的全部内容复制到新版本：
- Profile（基本信息）
- Education（教育经历）
- Experience（工作 + 项目）
- Skill（技能）

荣誉证书和作品集按姓名归档，不跟版本走。如果两个版本姓名相同，自动共享同一套荣誉和作品集。

**知识点**：克隆时的做法是查源版本全部记录，然后把每条记录的 `id` 置 null、`version_id` 改成新版本 id，再逐条 insert。利用 MyBatis-Plus 的 `insert()` 方法，id 为 null 时数据库自增生成新 id。

### 第一个版本自动设为默认

如果是数据库里的第一个版本，创建后自动把 `is_default` 设为 1。

---

## 四、切换默认版本

### 数据库唯一索引的设计

`is_default` 字段上有唯一索引 `uk_version_default`，允许 NULL 但最多只能有一个 1。这样就能保证全局只有一个默认版本。

### 切换逻辑

```java
@Transactional(rollbackFor = Exception.class)
public void setDefault(Long id) {
    // 1. 把当前默认版本的 is_default 置为 NULL
    versionMapper.update(null, new LambdaUpdateWrapper<ResumeVersion>()
            .eq(ResumeVersion::getIsDefault, 1)
            .set(ResumeVersion::getIsDefault, null));
    // 2. 把目标版本的 is_default 置为 1
    version.setIsDefault(1);
    versionMapper.updateById(version);
}
```

**知识点**：这里用了 `LambdaUpdateWrapper.set()` 而不是 `updateById()`，因为 `updateById()` 默认会忽略实体里的 null 字段（MyBatis-Plus 的 FieldStrategy 配置）。用 Wrapper 可以显式地把 is_default 改成 NULL。

### 必须加事务

两个 update 必须在同一个事务里，否则执行到一半（第一步成功、第二步还没执行）时数据库里一个默认版本都没有了。

**知识点**：`@Transactional` 的 `rollbackFor` 默认只对 RuntimeException 回滚。`BusinessException` 继承自 RuntimeException，所以没问题。如果要让 checked exception 也触发回滚，需要显式配置。

## 五、删除版本

```java
@Transactional
public void delete(Long id) {
    if (is_default == 1) throw new BusinessException(400, "默认版本不可删除");
    // 级联删除版本下的所有内容
    educationMapper.delete(eq version_id = id);
    experienceMapper.delete(eq version_id = id);
    skillMapper.delete(eq version_id = id);
    profileMapper.delete(eq version_id = id);
    versionMapper.deleteById(id);
}
```

不删除荣誉证书和作品集（跟版本无关）。也不在数据库层面用外键约束做级联删除，而是在代码里显式 delete。这样做的好处是：可以在删除前加业务校验、可以精确控制删除顺序、不会被 ORM 的级联配置绕晕。

---

## 六、版本内容完整度评分（defaultVersionId 兜底）

理论上数据库最多一个默认版本（唯一索引保证）。但历史数据可能有多个 is_default=1（比如早期代码没做唯一约束时写入的）。`defaultVersionId()` 方法的处理是：

```
1. 查所有 is_default=1 的版本
2. 只有一个 → 直接返回
3. 多个 → 选内容最完整的那个（教育 + 经历 + 技能的记录数之和最大）
4. 一个都没有 → 退回 id=1
```

这样能避免命中只有空壳 Profile 的"半残"版本，导致 AI 问答等功能没有内容可用。

---

## 七、知识点总结

| 知识点 | 说明 |
|--------|------|
| 版本隔离 | 所有简历内容查询先经过 resolveVersionId，强制版本隔离，防访客越权 |
| 双重防越权 | 前端和后端都做了版本校验，后端 JWT 里的 versionId 是唯一可信来源 |
| 数据库唯一索引 | uk_version_default 保证最多一个 is_default=1，NULL 不冲突 |
| LambdaUpdateWrapper.set() | 绕过实体的 null 忽略策略，强制把字段设为 NULL |
| @Transactional 回滚范围 | 默认只回滚 RuntimeException，rollbackFor 可以扩展 |
| 代码级级联删除 | 不依赖数据库外键，代码里显式按顺序删除子记录 |
| Record 类作为参数 | 克隆版本时把对象的 id 置 null 再 insert，MyBatis-Plus 自动用数据库自增生成新 id |
